# 作者自創名稱的編註草稿指示

網站把紙本專文改寫成捲動式文章，泡泡下方可以掛「編註」（虛線按鈕，點開是一段說明，卡片註明「不是作者原文」）。一般術語的編註已寫好；作者或作者公司自創的名稱（模型、框架、方法、角色名稱）不能由網站替作者下定義，所以改用原文自己的說明來寫，由使用者逐則決定。

## 格式範本

先讀 `content/review/rewrite/notes/coined-draft.md`，照它每一節的結構寫：泡泡、讀者怎麼卡、原文相關段落（逐字節錄，標頁碼）、草稿 A（作者的說法＋本站理解）、草稿 B（只有作者的說法）、建議與不確定的地方。那份草稿已經由使用者審過，使用者的決定是：i-Proof 選 A、母提示詞選 A、AI 製作人選 B、市場 DNA 檔案「不加」（泡泡已說明內容，讀者也不卡）、CEPs 語境地圖改寫成原文重述。所以「建議不加」是正當選項。

## 要讀的檔案（派工訊息給短名、aNN 與名稱）

1. `content/review/compression/<短名>.current.reader.md`：讀者看到的整篇（〔Mxx〕是泡泡編號，［延伸］［編註］是已有的補充）。
2. `content/review/compression/blind/` 裡這篇最新一輪的 `<短名>.<版本>.newbie.json`、`.engineer.json`（用 ls 看有哪些版本；有 `current` 用 `current`，否則用 `after`）。
3. `content/fulltext/<aNN>.md`：原文全文。
4. `content/review/rewrite/notes/<短名>.json` 的 skipped：寫手記下的頁碼線索。

不要讀其他專案檔案，不要改任何檔案，只寫輸出檔。

## 規則

- 「作者的說法」只用原文有的意思，可以縮寫，不能加因果、目的、例子。「本站理解」是推論，要在「建議與不確定的地方」說根據。
- 每則草稿不含標籤與頁碼 ≤110 字；以句號結尾。
- 用字：全形標點、中英文之間半形空格；不用他／她；寫「AI Agent」不寫「AI 代理」；寫「佔」不寫「占」；不能有半形單引號或反斜線。原文節錄照原文逐字，不受用字規範限制。
- 指稱作者用英文名或「作者」，指稱文章用中文篇名，不寫 aNN。
- 泡泡已說明清楚、讀者不卡的，寫「建議不加」並說明理由，不必硬寫草稿。

## 輸出

1. `content/review/rewrite/notes/coined-<組>.md`：審閱用草稿，開頭一段說明這組含哪些名稱、你的建議總表（名稱｜建議 A／B／不加）。
2. `content/review/rewrite/notes/coined-<組>.json`：
```json
[{"slug":"<短名>","id":"<aNN>","bubble":"M15","term":"和泡泡裡一模一樣的字","A":"作者的說法：…（p.N）本站理解：…","B":"作者的說法：…（p.N）","rec":"A|B|不加"}]
```
JSON 的 A、B 要寫成實際放進網站的一段文字（含「作者的說法：」「本站理解：」標籤，頁碼用全形括號），不加的 A、B 留空字串。

寫完回覆一句：幾則建議 A、幾則 B、幾則不加。
