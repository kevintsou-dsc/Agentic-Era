## 1. 背景與目標

### 1.1 比賽
《決策智慧》10 週年 Vibe Coding 競賽。要交四樣東西：公開網址（免登入）、3 分鐘介紹、製作歷程、部署與資安自評。

| 評分項 | 配分 | 本作品的對應策略 |
|---|---|---|
| 閱讀體驗與內容策展 | 40 | 從讀者手上的問題切入，3 分鐘內完整體驗一輪；策展層與原文明確分層；引文自動逐字核對 |
| Vibe Coding 實作力 | 30 | 製作歷程完整記錄「AI 初稿 → 人工判斷 → 修改」；建置閘門確保沒有壞功能和斷鏈 |
| 部署思路與資安自評 | 15 | 靜態站＋安全標頭＋repo 衛生＋授權白名單，五個面向如實自評 |
| 創意與洞察 | 15 | 「為一個決策而讀」：把全書主張「AI 整理、人判斷」做成閱讀方式本身 |

### 1.2 產品目標
- **G1 毫無壓力地進來**：第一次來的讀者不讀任何說明，只要往下捲動，1 分鐘內就能看懂全書在談什麼、分幾章、有哪幾條主線。
- **G2 讀完**：每篇文章都有一個約 90 秒的捲動故事（精華），讀者在一篇裡不需要做任何選擇就能讀到結尾。
- **G3 留下印象與收穫**：每篇故事結尾都帶走 2–3 個原文裡的問題或做法，並附紙本頁碼。
- **G4 找得到**：想找特定文章或同事文章的讀者，從首頁 2 次點擊內到達。
- **G5 正確**：每一則引文、數字、標題、作者、職稱都可回溯到刊物頁碼，正確率 100%，由建置閘門保證。

### 1.3 非目標
- 不做 AI 聊天問答，不串即時 LLM，不設後端。
- 不做 3D 場景，也不做捲動劫持（scroll-jacking）：捲動速度永遠由讀者控制。
- 不重現紙本翻頁。
- 不為互動而互動：每個點擊、拖拉都必須是「在關鍵處幫助理解細節」。

## 2. 核心洞察與差異化（v2，結構 C）

**洞察**：《決策智慧》內容紮實，但全書約 14.3 萬字、讀完要 5 小時 15 分。四個官方範例在「書的形狀」上下了很多功夫（空間、3D 塔、影像、翻書），讀者卻要先學會操作，注意力被元素分散。我們反過來：**讀者唯一要做的事是往下捲動**，精華內容與數據會依序出現，像看一個故事。

**三層閱讀深度**，讀者自己決定要讀多深：
1. **全書故事**（首頁，約 1–5 分鐘）：核心命題、四章、四條主線、6 張關鍵圖表。
2. **單篇故事**（每篇約 90 秒）：一句話主張、2–4 個關鍵場景（數據或框架）、帶走的問題。
3. **原文**（每篇 7–37 分鐘）：經校正的全文，標示紙本頁碼。

**影片用的一句話**：
> 這本書要 5 個小時才讀得完。我們把它變成一個故事：你只要往下捲，1 分鐘看懂全書，90 秒讀完一篇，想深讀再看原文。

**優先順序**：① UI/UX → ② 資訊視覺化 → ③ 炫技。每加一個效果之前先問：它有沒有讓讀者更快讀懂？

## 3. 使用者與情境

| 角色 | 情境 | 成功標準 |
|---|---|---|
| R1 冷啟動評審 | 收到網址，筆電打開，沒讀說明，約 3 分鐘 | 捲完首頁全書故事，並讀完至少一篇 90 秒故事 |
| R2 找特定文章的主管或同仁 | 想看某位同事寫的那篇 | 首頁 → 依章節找文章 → 文章，2 次點擊內 |
| R3 手機讀者 | 從分享連結直接進入單篇 | 知道這篇屬於哪一章、哪條主線，讀完後能接著讀同線文章 |
| R4 想深讀的讀者 | 對某篇有興趣 | 從 90 秒故事一鍵進入原文，原文頁碼可對照紙本 |

**驗收情境（評審旅程）**：一位同仁打開網址，不讀任何說明，在 3 分鐘內捲完全書故事、讀完一篇 90 秒故事，並找到自己同事的文章。

## 4. 資訊架構

```
/                    全書故事（首頁）：核心命題 → 四章 → 四條主線 → 依章節找文章
/a/<slug>/           單篇 90 秒故事
/a/<slug>/full/      原文（校正後全文，標紙本頁碼）
/about/              關於本作品：策展方法（AI 與人的分工）、出處與著作權、隱私說明、製作歷程、原始碼
/404                 找不到頁面：回首頁、依章節找文章
/llms.txt            機器可讀摘要（P1，自動產生）
```
slug 規則：`p<紙本起始頁>`，例如〈別買曝光了〉是 `/a/p72/`。只用 ASCII，跟紙本頁碼直接對應，讀者拿著紙本也能猜到網址。

## 5. 功能需求

### 5.1 全書故事（首頁，P0）
捲動順序：
1. **開場**：刊物識別＋核心命題「品牌離 AI 越近，會離人越遠嗎？」，以及「22 篇、30+ 位作者、原文約 5 小時，這裡 1 分鐘帶你看懂」。
2. **核心命題原文**：邵懿文〈Agentic 時代〉的命題句，附紙本頁碼。
3. **全書地圖**：22 個點依四章排列，捲動時依序點亮四條主線，每條主線附一句策展者整理與「讀這條線」入口。
4. **關鍵數據**（P1）：6 張關鍵圖表各一個場景（見 content-map §2.1）。
5. **依章節找文章**：四章卡片列出標題、全部作者、紙本頁碼、「90 秒」標記。這是首頁唯一的列表，也是 R2 的入口。
6. **頁尾**：關於本作品、原始碼、隱私說明。

### 5.2 單篇 90 秒故事（P0）
資料驅動的場景序列（`src/content/stories/p72.ts` 這類檔案），版型共用：
- **開場**：章節色、標題（內頁）、全部作者與職稱、紙本頁碼、「精華約 90 秒｜原文約 N 分鐘」、一句話主張（標「策展者整理」）。
- **場景**（2–4 個），可用的場景類型：
  - `graphic`：固定圖形＋捲動文字卡（數據圖表或框架逐步點亮）
  - `quote`：原文引文（引號＋紙本頁碼）
  - `bignum`：單一大數字（動態跑數一次）
  - `statement`：策展者的一句轉折
- **帶走的問題**：2–3 個原文中的問題或做法，附頁碼。
- **結尾導覽**：「讀原文（約 N 分鐘）」、「同一條主線的下一篇」、「回到全書」。
- 從分享連結直接進來的讀者，頁首會顯示「本篇屬於 People 章｜主線：從注意力到記憶」。

### 5.3 原文頁（P0）
- 頁首同單篇，加上「回到 90 秒精華」。
- 內文以 `content/fulltext/<id>.md` 渲染，每頁開頭標示「紙本 p.xx」，標題層級保留。
- 圖表、照片不重製，改以「此處為原刊圖：〈圖說〉」文字標示（圖說取自原文）。
- 全文需人工校正後才上線；未校正的文章先不開放原文頁，按鈕顯示「原文校正中」。

### 5.4 關於頁（P0）
策展方法（AI 與人的分工、逐字比對閘門）、出處與著作權聲明（「所載編輯內容之著作權為本刊所有」）、編輯團隊（不含聯絡方式）、隱私說明、製作歷程與 GitHub 連結。

### 5.5 P1
全書故事裡的 6 張關鍵圖表場景；同線下一篇；已讀標記（localStorage，只存文章 id）；llms.txt 與 JSON-LD；GA4（K13 待定，含捲動深度事件）。

### 5.6 P2（做不完整就不上線）
「給 AI 讀的版本」切換；分享卡片圖（OG image）逐篇產生。

### 5.7 狀態規則
- 已讀數為 0 時不顯示；localStorage 不可用時，整個進度元件隱藏。
- `prefers-reduced-motion` 開啟時關閉所有轉場，圖形直接顯示最終狀態。
- 圖形狀態由捲動位置直接算出（不依賴跨線事件），重新整理或快速捲動都正確。
- 404 頁提供回首頁與依章節找文章。

## 6. 內容與策展規格

### 6.1 單篇故事的策展規則
- 每篇 2–4 個場景；優先用原文裡**已有的圖表或框架**（content-map §2.1、§2.3），沒有圖表的文章用 `quote` 與 `bignum`。
- 策展者整理一律第三人稱、不加引號，卡片標「整理：策展者」；原文一律加引號並附「紙本 p.xx」。
- 原文標示為「示意圖」的圖表（例如〈文化暗流〉雷達圖），網站必須同樣標示。
- 不同來源、不同母體的百分比不畫在同一個軸上。
- 22 篇的故事都要經人工審定（`reviewed: true`）才上線。

### 6.2 每篇策展欄位（`content/articles/<slug>.json`，用 zod schema 驗證）
`id, slug, chapter, printPageStart, printPageEnd, titleInner, titleXlsx, titleToc, authors[{name, nameEn, title}], whyRead, keyPoints[3], keyFigures[{text, page}], quotes[{text, page}], takeaways[], fulltextPath, readMinutes`

### 6.3 正確性規則
- **標題**：以文章內頁標題為準（K4）；xlsx 與目錄的差異登記在 `content/title-exceptions.json`。
- **頁碼**：一律寫成「紙本 p.xx」，由單篇起始頁換算（起始頁見 `docs/design-review/facts-verified.md`）。
- **引文與數字**：必須是 `content/fulltext` 的逐字子字串（正規化後比對）。
- **作者與職稱**：以內頁為準，跟 xlsx 不一致的地方登記在例外清單。
- **關係標籤**：每條都要附兩邊的引文，並經人工核可（`approvedBy: human`）。
- **個資排除**：版權頁的公關 Email 不得進入 content 和 repo。

### 6.4 內容管線
1. `scripts/extract`（Python、PyMuPDF）：直接從 OneDrive 路徑讀單篇 PDF，依區塊座標「先欄後列」排序，排除頁眉、頁碼與註解，輸出 `content/fulltext/<slug>.md`，並標上頁碼。
2. 人工校正：每篇 15–25 分鐘，22 篇共 6–9 小時；抽樣 ≥ 10% 段落和 PDF 畫面比對。
3. AI 產出策展初稿（整理、論點、引文候選、回饋文字）→ 人工審定 → 在製作歷程記錄 diff 與理由。
4. `npm run verify` 閘門（見 §8）。

## 7. 視覺與互動規格

### 7.1 視覺語言
沿用刊物識別，詳見 `Content-Factory/creative-brief.md`。
- 牛皮紙底，同時保證文字對比 ≥ 4.5:1。
- 鉛筆素描（人）× ASCII 字元（AI）並置：作者觀點用手繪線條，結構化資料與頁碼用等寬字。
- 章節色：People 萊姆綠、Model 粉紅、AI 淺藍，Intro 用中性色。品牌色只用在色塊與線條上，色塊上的文字一律用深色。
- 鐳射漸層只用在主標與「換你判斷」的回饋卡。
- 字體：Noto Sans TC（子集化）、Montserrat、Pixelify Sans（頁碼與標籤）。

### 7.2 互動
CSS ＋ View Transitions 做頁面轉場；圓桌入場動畫 ≤ 600ms；不做捲動劫持；全流程可用鍵盤操作。

## 9. 部署與資安

### 9.1 部署（K3，建議 Cloudflare Pages）
- Cloudflare Pages 以 Git 整合部署，repo 和 CI 都不需要 token。使用預設網域 `*.pages.dev`，production 只從 `main` 部署。
- 11/20 起凍結 `release`；繳交前 24 小時不推 production；網址至少保留到 2026-12-31。
- `_headers`：CSP `default-src 'self'`（框架產生的 inline 以 hash 允許）、HSTS、`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`frame-ancestors 'none'`、`Permissions-Policy` 全部關閉。
- 備案 GitHub Pages：只能用 meta CSP，HSTS 等標頭無法設定，需在自評中寫明這個限制。

### 9.2 Repo 衛生（高風險）
- **git root 固定在專案資料夾**。上層工作區放有其他專案的設定檔，**禁止在上層 git init，也禁止整包上傳**（K8，使用者已確認上層安全）。
- `.gitignore` 採白名單式：先寫 `*`，再開放 `site/`、`content/`、`scripts/`、`docs/`、設定檔。
- pre-push 檢查：gitleaks 為 0 筆；`git ls-files` 不得出現 `.pdf/.indd/.idml/.xlsx/.ai/.psd`，也不得出現含 `private_key` 的 `.json`；dist 不輸出 sourcemap。

### 9.3 資安自評五個面向（繳交文件骨架）
1. 內容與圖像授權（K7：使用者確認所有素材皆可使用；網站仍標註圖片出處，案例截圖沿用刊物原有的「資料來源」說明）
2. Repo 衛生與機密掃描結果
3. 依賴（`npm audit` 不得有 high 以上漏洞、鎖定版本、執行期 0 個第三方網域）
4. 部署與安全標頭（附 securityheaders.com 或 Mozilla Observatory 檢測截圖）
5. 隱私（不蒐集資料、不提供自由輸入欄位、只用 localStorage、降級行為）
