# 單篇故事寫作規範（Story Guide）v1

> 2026-10-25。回應使用者回饋第 3 點：「主文有缺，讀起來不完整；主文要能連貫成完整文句，並與資訊圖表互補。」
> 所有 22 篇故事依此規範撰寫；`scripts/verify/lint-stories.mjs` 自動檢查其中可機械判斷的規則。

## 1. 兩條軌道：主文與旁資訊

每篇故事由兩條平行的軌道組成，**角色不能互換**：

| | 主文（Beat） | 旁資訊（Graphic／Panel／Quote） |
|---|---|---|
| 任務 | 把論點講完整 | 提供證據、結構與細節 |
| 讀法 | 只讀主文，也要能讀懂整篇的主張、理由與做法 | 不讀圖，主文也成立；讀了圖，理解更具體 |
| 形式 | 1–2 句完整的中文句子，第三人稱，40–110 字 | 圖表、框架、案例卡、原文引言 |
| 出處 | 每段至少一則 `src`，讀者點「紙本 p.xx」開書頁視窗 | 圖表註明資料來源；每個可互動元素可加 `detail`（hover／點擊看更多） |

**互補的意思**：主文說「是什麼、為什麼」，圖表說「多少、長什麼樣、細節在哪」。主文提到的關鍵數字，圖表一定要畫出來；圖表畫出來的重點，主文要用一句話說出它的意義。

## 2. 故事弧線（5–7 段主文）

| 段落 | 任務 | 常用場景 |
|---|---|---|
| ① 開場 | 一個讀者也會遇到的現象或問題 | quote（作者的開場原句）、bignum |
| ② 診斷 | 作者認為問題出在哪 | graphic（數據）、quote |
| ③ 證據 | 支撐診斷的數據或研究 | graphic：bars／hbars |
| ④ 框架 | 作者提出的解方或分析框架 | graphic：layers／matrix／cycle／list |
| ⑤ 案例 | 1–4 個具體案例 | **hscroll**（橫向捲動）、more |
| ⑥ 收束 | 一句總結，回到開場的問題 | quote、statement |
| 結尾 | 帶走的問題或做法（原文） | asks |

不是每篇都要七段，但**① ④ ⑥ 必備**。同一篇最多一個 hscroll，避免讀者疲乏。

## 3. 主文的硬規則（lint 自動檢查）

1. 每段主文以句末標點結束（。！？」），**不可以冒號結尾**，也不可以只寫「第二：」這種需要看圖才完整的半句。
2. 每段主文至少一則 `src`，且通過逐字比對。
3. 主文 30–140 字（含標點）。太短通常是半句，太長就拆成兩段。
4. 一篇的主文串起來（含一句話主張）約 500–1,000 字，讀完 60–120 秒。
5. 不用「XX 說：」句式；作者姓名出現時寫全名，不寫文章編號。

## 4. 主文的軟規則（Jev 初評＋人工校閱）

- **忠實**：主文的每個主張都能在 `src` 中找到依據，不誇大、不加入原文沒有的因果。
- **完整**：讀者只讀主文，能說出這篇的主張、一個理由、一個做法。
- **連貫**：相鄰兩段之間有邏輯銜接（因此、但、於是），不是條列拼貼。
- **好讀**：一句一個重點，避免連續三個以上的專有名詞。

## 5. 旁資訊的規則

- 圖表只畫原刊有的數據；原刊標「示意圖」的，網站也標示。
- 每個長條、節點、層級、清單項目都可以加 `detail`：hover 顯示一句話，點擊開書頁視窗並附原文。數據型圖表的每個值**都要有 detail**，說明這個數字的母體或條件（例如「注視 > 10 秒」是什麼意思）。
- hscroll 的每一格都要有完整主文與 `src`，不能只放標題與數字。

## 6. 審稿狀態

`status: 'draft' → 'judged' → 'reviewed'`

- draft：撰寫完成，通過 lint 與逐字比對。
- judged：通過 Jev 初評（門檻見 `docs/review-pipeline.md`）。
- reviewed：人工校閱完成。繳交前 22 篇都必須是 reviewed。
