# 單篇故事寫作規範（Story Guide）v1

> 2026-10-25。回應使用者回饋第 3 點：「主文有缺，讀起來不完整；主文要能連貫成完整文句，並與資訊圖表互補。」
> 所有 22 篇故事依此規範撰寫；`scripts/verify/lint-stories.mjs` 自動檢查其中可機械判斷的規則。

## 1. 兩條軌道：主文與旁資訊

每篇故事由兩條平行的軌道組成，**角色不能互換**：

| | 主文（Beat） | 旁資訊（Graphic／Panel／Quote） |
|---|---|---|
| 任務 | 把論點講完整 | 提供證據、結構與細節 |
| 讀法 | 只讀主文，也要能讀懂整篇的主張、理由與做法 | 不讀圖，主文也成立；讀了圖，理解更具體 |
| 形式 | 1–2 句完整的中文句子，第三人稱，40–110 字 | 圖表、框架、案例卡、原文引言 |
| 出處 | 每段至少一則 `src`，讀者點「紙本 p.xx」開書頁視窗 | 圖表註明資料來源；d3 圖表每個可互動元素都要有策展補充說明框（`extra`，見 §5.1）；原文寫進主文 |

**互補的意思**：主文說「是什麼、為什麼」，圖表說「多少、長什麼樣、細節在哪」。主文提到的關鍵數字，圖表一定要畫出來；圖表畫出來的重點，主文要用一句話說出它的意義。

## 2. 故事弧線（5–7 段主文）

| 段落 | 任務 | 常用場景 |
|---|---|---|
| ① 開場 | 一個讀者也會遇到的現象或問題 | quote（作者的開場原句）、bignum |
| ② 診斷 | 作者認為問題出在哪 | graphic（數據）、quote |
| ③ 證據 | 支撐診斷的數據或研究 | graphic：bars／hbars |
| ④ 框架 | 作者提出的解方或分析框架 | graphic：layers／matrix／cycle／list |
| ⑤ 案例 | 1–4 個具體案例 | **hscroll**（橫向捲動）、more |
| ⑥ 收束 | 一句總結，回到開場的問題 | quote、statement |
| 結尾 | 帶走的問題或做法（原文） | asks |

不是每篇都要七段，但**① ④ ⑥ 必備**。同一篇最多一個 hscroll，避免讀者疲乏。

## 3. 主文的硬規則（lint 自動檢查）

1. 每段主文以句末標點結束（。！？」），**不可以冒號結尾**，也不可以只寫「第二：」這種需要看圖才完整的半句。
2. 每段主文至少一則 `src`，且通過逐字比對。
3. 主文 30–140 字（含標點）。太短通常是半句，太長就拆成兩段。
4. 一篇的主文串起來（含一句話主張）約 500–1,000 字，讀完 60–120 秒。
5. 不用「XX 說：」句式；作者姓名出現時寫全名，不寫文章編號。

## 4. 主文的軟規則（Jev 初評＋人工校閱）

- **忠實**：主文的每個主張都能在 `src` 中找到依據，不誇大、不加入原文沒有的因果。
- **完整**：讀者只讀主文，能說出這篇的主張、一個理由、一個做法。
- **連貫**：相鄰兩段之間有邏輯銜接（因此、但、於是），不是條列拼貼。
- **好讀**：一句一個重點，避免連續三個以上的專有名詞。

## 5. 旁資訊的規則

- 圖表只畫原刊有的數據；原刊標「示意圖」的，網站也標示。
- 每個長條、節點、層級、清單項目都可以加 `detail`：hover 顯示一句話，點擊開書頁視窗並附原文。數據型圖表的每個值**都要有 detail**，說明這個數字的母體或條件（例如「注視 > 10 秒」是什麼意思）。

- **圖表元素上的細節不能佔版面**：長條、橫條、循環節點、層級、清單項目掛 `more` 時，一律用 `MoreRef overlay`。按鈕透明覆蓋整個元素，只在角落放一個小「＋」圓點；滑鼠移上去就預覽細節內容（標題＋前 110 字），點一下開完整細節卡，觸控裝置直接點開。不要把「＋細節」按鈕塞進標籤或數值旁邊，會把圖表擠歪。主文段落、橫向捲動卡片的細節，才用一般的「＋ 標題」按鈕。

- **數字的呈現要配得上數字的性質**：大數字（`bignum`）、長條、百分比只用在**統計數據**（調查、研究、收視、營收等有母體或來源的數字）。作者的親身經驗、小故事、舉例裡的數字（例如「大概二十個類似廣告」）不是統計，不要做成大數字或圖表，以免讀者誤以為是研究結果。
- **小故事用分格插畫**：作者經驗、案例情境這類有起承轉合的內容，用 `type: 'art'` 的分格插畫（`src/components/art/`）。每段主文對應一格（`data-focus`），捲到哪段就換到哪格，格內可以有輕量動畫；圖說標「插畫：策展者繪製｜依據 …」。插畫用 inline SVG＋CSS 繪製，不引用外部圖檔，顏色用全站色票變數。

### 5.1 d3 圖表的說明框（hover／聚焦／點擊）

說明框是讀者「想多懂一點」時的入口，**只放策展補充，不放原文**。

- **原文寫在左側主文**：圖表在講什麼、原文的數字與案例，一律寫進主文 beats（附出處）。圖表上的細項（例如生態系各面向列出的「影視、音樂、遊戲」）也要在主文交代，不要只藏在說明框裡。
- **出處整張圖只標一次**：圖說文字（`source`）寫資料來源與紙本頁碼，加上場景的 `src`（「這張圖出自 原文 p.xx」）。說明框裡不再放頁碼或「原文整理」。
- **每個可互動元素都要有 `extra`**：flowloop 的圓心與每個節點、stages 的每一列（模型名稱）與每一格、groups 的每個值、logrange 的每一列。說明框標「策展補充（非原文）」。lint 檢查：`extra` 至少 40 字；出現 `detail`／`centerDetail` 會被擋下。
- **補什麼**：原文沒講、但讀者需要才看得懂的東西，例如名詞定義、模型的由來與提出者、和前一個時代的差別、一個具體的例子、這件事對品牌的意義。原文資訊不足時大膽補，不要硬對齊原文。
- **補充要可靠**：只寫一般公認的知識（定義、普遍引用的出處、常見案例）。沒把握的年份、數字、人名不寫；不替原文作者發言；不在圖上加原文沒有的數據。`extra` 不經 verify-quotes 比對，人工校閱時要特別檢查。
- **寫法**：2–4 句，先說「這是什麼」，再說「為什麼重要／和前後的關係」，能舉例就舉例，每則約 50–120 字。每則要能單獨讀懂，不要用「例如…」開頭。

### 5.2 案例圖片的畫質

- 圖片一律由 `scripts/extract/extract_figures.py` 依 PDF 內嵌的原始解析度抽出（最長邊 1600px、WebP 品質 86），不要再手動縮小。
- 原始素材本身就很小的（例如作者提供的 400–600px 截圖），網頁上不放大超過原始像素寬；橫幅型圖片（寬高比 > 2.2）在卡片中完整顯示、不裁切。
- 不直接引用外部網站的圖片網址（hotlink）：CSP 只允許站內資源、外部連結會失效，也會把讀者的瀏覽資訊送給第三方。若某張圖真的太糊，改為向來源取得高解析官方圖，經確認可使用後存進 `public/fig/`，並在 credit 註明出處。

## 6. 審稿狀態

`status: 'draft' → 'judged' → 'reviewed'`

- draft：撰寫完成，通過 lint 與逐字比對。
- judged：通過 Jev 初評（門檻見 `docs/review-pipeline.md`）。
- reviewed：人工校閱完成。繳交前 22 篇都必須是 reviewed。
